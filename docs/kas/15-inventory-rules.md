# 15 — Inventory Rules

**Status of this document:** Phase 1 specification for approval
**Last updated:** 2026-08-14

> **CONFIRMED requirement:** the system must prevent customers from requesting more rooms than
> available inventory. This document specifies exactly how that guarantee is delivered.

---

## 1. Model

**CONFIRMED** — Admin manages total, available, reserved, occupied, and maintenance inventory.

**PROPOSED** — Inventory is tracked **per room type, per date**:

```
room_type_inventory_day (room_type_id, date)
    total          units that physically exist
    ota_allotment  transitional buffer for OTA distribution  (see §7)
    ota_reserved   OTA reservations recorded in KAS          (see §7)
    reserved       DIRECT holds and confirmed direct stays
    occupied       units currently in use by an in-house guest
    maintenance    units out of service
    other_blocks   group holds, owner use, staff, contingency
```

**The derived value:**

```
availableDirect(roomType, date)
    = total − ota_allotment − reserved − occupied − maintenance − other_blocks
```

**Invariant, enforced by a database CHECK constraint:**

```
total − ota_allotment − reserved − occupied − maintenance − other_blocks ≥ 0
```

> ⚠ `ota_reserved ≤ ota_allotment` was specified in an earlier draft and is **withdrawn** — see §7.2.

## 2. Core decisions

**PROPOSED** — Three decisions that make the guarantee structural rather than aspirational.

### 2.1 `available` is derived, never stored as an editable field

If an operator could type an availability number directly, that number could disagree with the
component counts, and the disagreement would be invisible until a guest was turned away. Admin edits
`total`, `maintenance`, and `occupied` (where no PMS exists); `reserved` is moved only by the system;
`available` is computed.

### 2.2 The guarantee lives in the database

Application logic can have bugs. A `CHECK` constraint cannot be bypassed by a bug in a service, a
missing validation, a race condition, or a direct admin action. **PostgreSQL refuses to write a row
that would oversell.** Every layer above it is an optimisation for user experience, not the guarantee
itself.

### 2.3 Per-date granularity

A stay of *N* nights consumes inventory on *N* dates. Availability is therefore checked and reserved
per night, not per booking. This is the only model that handles overlapping stays of different
lengths correctly.

## 3. Date semantics

**PROPOSED** — Precise, because off-by-one errors here cause real oversells.

- A stay from **check-in D1** to **check-out D2** occupies nights `D1, D1+1, …, D2−1`.
- The check-out date is **not** occupied.
- Nights = `D2 − D1`.
- Example: 12 Sep → 14 Sep occupies the nights of **12 Sep and 13 Sep**. Two nights.
- All dates are property-local calendar dates in **Asia/Ho_Chi_Minh (UTC+7)**. Timestamps are stored
  in UTC; **inventory dates are calendar dates, not timestamps**. Conflating the two produces
  midnight-boundary bugs.

## 4. Availability algorithm

**PROPOSED**

### 4.1 Single room type

```
isAvailable(roomTypeId, checkIn, checkOut, quantity):
    nights = dateRange(checkIn, checkOut - 1 day)
    for each night in nights:
        row = inventoryDay(roomTypeId, night)
        if row is missing:            return false   // outside the published horizon
        if available(row) < quantity: return false
    return true
```

`minAvailable` across all nights is what the guest sees as "N rooms available" — the **minimum**, not
the average and not the first night. Showing anything else would advertise capacity that does not
exist for the whole stay.

### 4.2 Multiple room types in one request

```
isRequestAvailable(lines[], checkIn, checkOut):
    for each line in lines:
        if not isAvailable(line.roomTypeId, checkIn, checkOut, line.quantity):
            return false
    return true
```

Room types are independent — each has its own inventory pool — so no cross-line interaction exists
unless rate plans are introduced later (OQ-034).

### 4.3 Property-level availability

A property is shown as available for a date range if **at least one** published room type has
`available ≥ 1` on every night. The property's "from" price is the lowest nightly price among
available room types.

### 4.4 Publication horizon

**PROPOSED** — Inventory rows exist for a rolling **24-month** horizon, generated by a scheduled job
that seeds each new date from the room type's default `total`. Requests beyond the horizon are not
"unavailable" — they are **not yet open for booking**, and must be worded that way with an invitation
to enquire directly.

## 5. Reservation and the last-room race

**PROPOSED** — The mechanism preventing two guests from requesting the same last room.

### 5.1 Transaction

```
BEGIN;

-- 1. Lock every affected inventory row, in a deterministic order
--    (room_type_id, then date) to eliminate deadlock between concurrent requests
SELECT * FROM room_type_inventory_day
 WHERE (room_type_id, date) IN (:allLineNights)
 ORDER BY room_type_id, date
   FOR UPDATE;

-- 2. Re-verify availability under the lock
--    (the check the guest saw seconds ago is no longer authoritative)
--    If insufficient → ROLLBACK and return a domain error with alternatives

-- 3. Increment reserved for every line-night
UPDATE room_type_inventory_day
   SET reserved = reserved + :quantity
 WHERE room_type_id = :rt AND date = :d;
--    The CHECK constraint fires here if anything is wrong. Nothing gets through.

-- 4. Create the booking, booking lines, and price snapshot
-- 5. Create inventory_hold rows with expires_at
-- 6. Write booking_status_history (DRAFT → REQUESTED)

COMMIT;

-- 7. AFTER commit: emit the domain event → acknowledgement email, sales notification
```

**PROPOSED — three points that matter:**

1. **Deterministic lock ordering** is what prevents deadlock. Two concurrent requests touching the
   same rows in different orders will deadlock; in the same order, one simply waits.
2. **Re-verification happens under the lock.** The availability the guest saw on screen is a snapshot
   and is never trusted at submission time.
3. **Emails are emitted after commit**, never inside the transaction. An email provider outage must
   not roll back a booking, and a rolled-back transaction must not have sent an email.

### 5.2 Concurrency test — a release gate

**PROPOSED** — Fire *N* simultaneous requests for the last available room and assert:
exactly one succeeds; the rest receive a clean domain error; `available` ends at 0; `reserved`
matches exactly one booking. This test is **blocking in CI**. It is the direct verification of a
confirmed business requirement.

## 6. Holds

**PROPOSED** — Recommended model, pending OQ-018.

| Property | Value |
|---|---|
| Created on | Transition to `REQUESTED` |
| Duration | **24h** default, configurable per property |
| Effect | `reserved += quantity` for every night of the stay |
| Visibility | Admin-visible as *held*, distinct from *confirmed*; **never** exposed to guests |
| Extension | Admin may extend; extended automatically on `AVAILABILITY_CONFIRMED` |
| Becomes firm | On `CONFIRMED` — `expires_at` cleared |
| Released on | `CANCELLED`, `EXPIRED`, `NO_SHOW`, or expiry sweep |

### 6.1 Expiry sweep

**PROPOSED**

```
every 5 minutes:
    holds = SELECT … WHERE expires_at < now() AND released_at IS NULL
    for each booking with expired holds:
        BEGIN
          lock affected inventory rows (ordered)
          reserved -= quantity for each hold
          mark holds released
          transition booking → EXPIRED with reason HOLD_EXPIRED
          write status history
        COMMIT
        after commit: notify guest and assigned agent
```

Idempotent by design: a hold already marked released is skipped, so a re-run cannot double-decrement.

### 6.2 Why holds, honestly

A soft hold means a speculative request can block a real one for up to 24 hours. That is a genuine
cost. It is accepted because the alternative — promising the same room to several guests and letting
sales disappoint most of them — is far more damaging to a brand whose thesis is personal hospitality.
Mitigations: a short window, admin visibility of held vs. confirmed, rate limiting, duplicate
detection, and the ability to release a hold manually.

## 7. Reconciliation

**NEEDS CONFIRMATION** — Where inventory truth lives today (OQ-011). This is the largest operational
risk in the system.

> ⚠ **CORRECTED.** An earlier draft of this section treated all non-website reservations as one class
> of "manual booking" with a generic `source` field. That is wrong. **OTA reservations and direct
> phone/walk-in leads are different things** — different distribution channel, different sales process,
> different reporting — and must never share a field. See
> [29-direct-sales-crm-architecture.md](29-direct-sales-crm-architecture.md).

**PROPOSED** — Central inventory accepts three classes of consumption, all identical in their effect on
availability and entirely different in how they originate:

| Consumer | Channel | Enters inventory via |
|---|---|---|
| **Direct reservations** | `DIRECT` — website, Facebook, Zalo, TikTok, Instagram, phone, walk-in, referral, returning | The direct lead workflow ([29](29-direct-sales-crm-architecture.md) §5) |
| **OTA reservations** | `BOOKING_COM`, `AGODA`, `CTRIP`, `TRAVELOKA` | Allotment or manual register entry — **never the sales queue** |
| **Operational changes** | — | Admin: `maintenance`, `total`, occupancy |

**PROPOSED** — The channel-aware inventory day carries `ota_allotment` and `ota_reserved` alongside the
existing counts:

```
availableDirect = total − ota_allotment − reserved − occupied − maintenance
```

### 7.1 The V1 model — HYBRID TRANSITIONAL (D-34, amended)

**CONFIRMED (Phase 3)** — KAS Admin is the **operational hub** (D-28). KAS is **not** locked into pure
allotment, and **not** locked into pure manual entry. V1 uses a **hybrid transitional model**.

> ⚠ **This supersedes the earlier "allotment first" recommendation.** That recommendation was correct
> *given the assumption that OTA reservations might never be recorded*. The operational hub decision
> removes that assumption: OTA reservations **are** recorded, so allotment stops being the oversell
> defence and becomes a shrinking **safety buffer**.

```
OTA (Booking.com | Agoda | Ctrip | Traveloka)
        │  reservation received in the extranet
        ▼
   KAS Admin records / imports it            ← TRANSITIONAL — V1 only
        ▼
   CENTRAL RESERVATION   (one entity, stayStatus = CONFIRMED, salesStatus = NULL)
        ▼
   CENTRAL INVENTORY     (ota_reserved)
        ▼
   Operations: arrivals · occupancy · departures
```

| Layer | Role in V1 | Retirement |
|---|---|---|
| **Safety buffer** `ota_allotment` | Protects against oversell while recording discipline is unproven | Shrinks toward 0 |
| **Recording** `ota_reserved` | Operational truth — arrivals, occupancy, Customer 360, review eligibility | Automated by the channel manager |
| **Channel manager** | — | **FUTURE.** Real-time two-way sync makes both unnecessary |

### 7.1a The safety buffer is configurable, not fixed (OQ-074)

**CONFIRMED (Phase 3.5)** — **No universal percentage or room count is hard-coded.** The buffer is
admin-configurable by **property + room type + date range / season**, via
`ota_safety_buffer_rule` ([13](13-database-domain-overview.md) §3.4c).

| Dimension | Why it must be configurable |
|---|---|
| **Property** | Eight properties with different OTA dependence. One number cannot fit all |
| **Room type** | A room type an OTA sells heavily needs a different buffer from one it rarely sells |
| **Date range / season** | Tết, holidays and high season have entirely different channel behaviour |

**PROPOSED mechanics:** rules resolve by priority, most specific first; `PERCENTAGE` is of `total` and
**rounds up**; the effective buffer is **clamped** so it can never drive availability negative:

```
effectiveBuffer = min(configuredBuffer,
                      total − reserved − occupied − maintenance − other_blocks)
```

> ⚠ **NEEDS CONFIRMATION — OQ-074.** **No initial value has been invented.** Buffer values per
> property, room type and season are a **business configuration required before production launch**.
> The system ships with the mechanism and **no default rule** — with none configured,
> `ota_allotment = 0`. Sizing needs the channel volume data still open under **OQ-033**.

### 7.1b Retirement path

**PROPOSED** — Sequenced so the buffer retires on evidence rather than optimism. **Thresholds below
are placeholders requiring business approval — none is an approved SLA.**

```
Stage 1 (launch)   Buffer configured per property/room type/season + manual recording
Stage 2            Buffer reduced as recording reliability is measured
Stage 3            Buffer minimal. Recording is the operational truth
Stage 4 (FUTURE)   Channel manager. Buffer → 0. Recording automated
```

**Stage-2 exit criteria — the *measurements* are defined; the *thresholds* are not:**

| Measurement | Threshold |
|---|---|
| OTA recording lag (received → recorded) | **Business-supplied — OQ-081.** Not invented here |
| Unexplained buffer overflows | **PROPOSED**: zero, over a business-agreed observation period |
| Daily reconciliation variance vs the extranets | **PROPOSED**: a business-agreed tolerance |

**CONFIRMED** — Manual OTA entry is **transitional, not permanent architecture**. Every screen, process
and metric supporting it is labelled `TRANSITIONAL — V1` in admin so the organisation does not quietly
accept it as normal.

### 7.1c Who records OTA reservations (OQ-075)

**CONFIRMED (Phase 3.5)** — OTA reservations are **operational**, not a KAS Sales responsibility.

```
OTA  →  Hotel operational staff / authorised Admin  →  Record in KAS
     →  Central Reservation  →  Central Inventory update
```

| | |
|---|---|
| **Who** | Property Admin · Reservation Staff · Front Desk *(V1: property-scoped `ADMIN`)* |
| **Never** | KAS Sales. No sales owner is created — enforced by the CHECK constraint |
| **Channel** | Recorded explicitly: `BOOKING_COM` · `AGODA` · `CTRIP` · `TRAVELOKA` |
| **Timing** | **As soon as operationally possible after receipt.** No numeric SLA specified — **OQ-081** |
| **Permission** | `reservation.ota.record`, property-scoped ([06](06-user-roles.md) §4) |

### 7.2 Recording overflow — availability fails closed, recording fails open

**PROPOSED — a correction to an earlier constraint.** An OTA can sell beyond its allotment when the
extranet is stale. The system must **never refuse to record a real reservation**:

```
recordOtaReservation(roomType, dates, qty):
    if ota_reserved + qty > ota_allotment:
        ota_allotment := ota_reserved + qty     -- auto-expand, consuming direct availability
        ALERT "OTA allotment exceeded"          -- operations must know
    ota_reserved += qty
    if the oversell CHECK would now fail:
        RECORD ANYWAY, RAISE P1                 -- the property is genuinely oversold;
                                                -- this needs a human, not a rejected insert
```

**The principle:** refusing to **sell** when uncertain is correct. Refusing to **record reality** is
not — the guest exists and is arriving regardless of what our numbers say.

**PROPOSED** — A **daily reconciliation report** compares KAS's position against the property's actual
position and flags discrepancies, under any strategy.

**FUTURE** — A channel manager makes the choice moot: it pushes availability and rates to the OTAs and
pulls reservations back, behind a `ChannelManagerProvider` port. **Do not assume any specific OTA API.**

Strategy decision: **OQ-067**. Volume and mix per channel: **OQ-033**. Whether OTA reservations must be
recorded at all: **OQ-070**.

## 8. Admin operations

**PROPOSED**

| Operation | Rules |
|---|---|
| Change `total` | Cannot reduce below `reserved + occupied + maintenance` on any affected date. Blocked with an explanation naming the conflicting dates |
| Set `maintenance` | Cannot exceed `total − reserved − occupied`. Requires a reason. Affected confirmed bookings are surfaced before saving |
| Bulk edit by range | Preview of every affected cell before commit; conflicts listed rather than silently skipped |
| Block a date range | Sets `maintenance = total` — a room type genuinely closed for a period |
| Release a hold | Permission-gated; reason required; guest notified |
| Manual booking | Consumes inventory identically to a web request |

Every change is audit-logged with actor, before, after, and reason.

## 9. Displaying availability

**PROPOSED**

| Situation | Display |
|---|---|
| `available ≥ 1` and comfortable | "Available for your dates" |
| `available` is low but real | "**3 rooms available**" — **only when literally true** |
| `available = 0` for this room type | "Not available 12–14 Sep" + nearest available dates |
| `available = 0` for the whole property | Property shown, marked unavailable, with alternative dates and other KAS properties |
| Beyond the horizon | "Not yet open for booking — contact us" |
| Availability service unhealthy | "Availability temporarily unavailable — please contact us" — **never a guessed number** |

**PROPOSED** — Scarcity messaging is derived directly from inventory and never manufactured. This is a
brand rule ([02](02-brand-foundation.md) §6.1) as well as a correctness rule.

## 10. Caching

**PROPOSED** — Availability is the one thing that must not be stale.

| Data | Cache | TTL |
|---|---|---|
| Property and room type content | CDN + HTTP cache | Hours; invalidated on publish |
| Images | CDN | Long, content-hashed |
| Availability search results | Redis | **≤ 60s**, invalidated eagerly on any inventory change for the affected room type and dates |
| Availability at submission | **Never cached** | Always read under lock from the database |

The submission path reads live, locked data. Caching serves browsing speed only.

## 12. Failure modes and responses

**PROPOSED**

| Failure | Response |
|---|---|
| Availability lost between selection and submit | Clear explanation, alternatives offered, rest of the selection preserved. **Never a silent quantity reduction** |
| Database unavailable at submit | Request fails visibly with a correlation ID and a contact route. **Never a silent success** |
| Hold expiry job stops running | Monitored; alert on queue lag; holds continue to block until swept — degraded but safe |
| Inventory rows missing for a date | Treated as unavailable, never as unlimited. **Fail closed** |
| Negative count somehow attempted | Database rejects; error alerted as a P1 defect |
| Clock skew across servers | Single time source; dates computed in the property timezone |
| Duplicate submission | Idempotency key; the second attempt returns the first booking rather than creating a second |

**PROPOSED — the governing principle:** every inventory failure mode **fails closed**. When the system
is uncertain, it declines the request. A lost booking is recoverable through a phone call; an
oversold room is a guest standing in a lobby with nowhere to sleep.
